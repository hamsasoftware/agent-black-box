# Summary

Implemented `plan_retention()` in `vaultsnap/retention.py`.

Which ADRs I applied: the overall model (set-aside snapshots, keep_last, independent bucket rules that skip empty periods, output order) is ADR-0001. Its "Weeks" section is superseded, so weekly buckets are ISO weeks per ADR-0003. ADR-0002 (UTC days) is superseded by ADR-0004: every bucket key comes from `taken_at` converted to the offset, then shifted back by `day_start_hour`; `keep_last` and the future check use the real instant. ADR-0005 replaces only the "no zone names" sentence of ADR-0004: with `zone` set, the offset is looked up in the zone table at the real instant and `tz_offset_minutes` is ignored. ADR-0006 adds `keep_within_hours` (inclusive, real instants) as a sixth rule, but its section on the bucket rules was reverted by ADR-0009, so window snapshots are set aside (kept, not counted, never a representative). ADR-0007 adds the dependency step: after all rules, ancestors of kept snapshots are held; held snapshots count toward nothing. ADR-0008 gives `expire_tags` and the order of overrides (protect, future, expire, then ADR-0009's window, then the remaining snapshots), with the dependency step overriding expiry. ADR-0010 makes monthly buckets start on `month_start_day` with short months and leap years handled; yearly stays the calendar year. The docs/adr/README.md index stops at ADR-0007 and its status column is out of date, so I used the status line of each record instead. The README draft in the project root is older than the ADRs and was ignored.

Verified: `python -m unittest` (7 visible tests OK), plus a scratch script that checked the New Year weeks, a day start crossing a year, both zones around a transition, the window with keep_daily, a held parent that is newer than its child, expired snapshots, and month start day 31 around 29 February. Not verified: very large snapshot lists for speed.
